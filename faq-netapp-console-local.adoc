[[get-started-with-netapp-console-local-deployment]]
== NetApp Consoleのローカル展開を開始する

.NetApp Console のローカル展開とは何ですか？また、セルフホストオプションを使用する理由は何ですか？
NetApp Console のローカル展開は、コンソール制御プレーンをお客様自身のオンプレミス環境で実行するセルフホスト型の展開オプションです。ストレージ管理と自動化（プロビジョニング、ポリシー適用、ドリフト検出、修復）を統合し、データ、メタデータ、管理トラフィックをお客様自身のインフラストラクチャ内に完全に保持することで、データ主権を損なうことなく運用上の優位性を実現します。link:concept-netapp-console-local.html["NetApp Console のローカル展開について"]。

.NetApp Console のローカル展開をデプロイするにはどうすればよいですか？
事前設定済みのOVAイメージを使用し、お客様のVMware vCenter環境に仮想アプライアンスとしてNetApp Consoleローカルデプロイをデプロイします。デプロイ後、ストレージを検出し、メンバーを追加してロールを割り当てることで、使用を開始できます。link:concept-deploy-netapp-console-local.html["導入オプションについて"].

.NetApp Console のローカル展開を使用するには、ライセンスまたはサブスクリプションが必要ですか？
いいえ。NetApp Console のローカル展開の使用を開始するのに、ライセンスやサブスクリプションは必要ありません。ただし、NetApp Backup and Recovery など、Console のローカル展開からアクセスできる一部の NetApp データサービスは、ライセンス制またはサブスクリプション制であり、費用が発生する場合があります。

.NetApp Console のローカル展開におけるストレージ管理の推奨設定手順は何ですか？
一般的なワークフローは、ストレージシステムを適切なフリートに検出し、ストレージクラスポリシーを定義し、それらのポリシーからストレージクラスを作成し、適用可能なフリートにクラスを関連付け、クラスを使用してボリュームまたはLUNをプロビジョニングし、その後、ドリフトを監視してワークロードを整合させるための修復を行うというものです。link:concept-manage-storage.html["ストレージの管理について"]。



[[storage-classes-and-policies]]
== ストレージクラスとポリシー

.ストレージクラスとは何ですか？また、なぜストレージクラスを使用するのでしょうか？
ストレージクラスとは、組織のストレージ標準（パフォーマンス、容量、セキュリティ、データ保護など）を、ストレージクラスポリシーから構成される単一の名前付きオブジェクトにまとめた、再利用可能なテンプレートです。ストレージクラスを使用してプロビジョニングを行うと、コンソールのローカルデプロイメントはワークロードごとの構成決定なしにこれらの標準を自動的に適用し、その後、ワークロードをクラスに対して監視し、準拠から逸脱した場合は警告を発します。link:concept-storage-classes.html["ストレージクラスについて"]。

.ストレージクラスポリシーとは何ですか？また、ストレージクラスとどのように関連していますか？
ストレージクラスポリシーは、ストレージクラスを構築するために組み合わせる構成要素です。各ポリシーはストレージ動作の1つの側面を規定するため、ポリシーは個別に定義し、それらをまとめてクラスを作成します。これにより、複数のクラスで同じポリシーを再利用したり、ポリシーを1箇所で更新して、その変更をポリシーを使用するすべてのクラスに適用したりすることが可能になります。link:concept-storage-class-policies.html["ストレージクラスポリシーについて"]。

.どのような種類のストレージクラスポリシーを作成できますか？
NetApp Console のローカル展開には、4種類のストレージクラスポリシーが含まれます：

* *パフォーマンス ポリシー*：配置およびドリフト検出に使用される、期待される IOPS/TB、ピーク IOPS/TB、絶対最小 IOPS、および期待されるレイテンシのターゲットを設定します。
* *容量ポリシー*：スペース リザベーション、自動拡張、FabricPool 階層化、および NAS 向け FlexVol または FlexGroup プロビジョニングを制御します。
* *セキュリティポリシー*：暗号化、ランサムウェア対策、およびFIPS要件を設定します。
* *データ保護ポリシー*：一貫性のあるバックアップスケジュールを実現するために、各間隔で保持するスナップショットの数を設定します。


link:concept-storage-class-policies.html["ストレージクラスポリシーについて"].

.ストレージクラスとポリシーをゼロから構築する必要があるのでしょうか？
いいえ。コンソールのローカル展開には、4つのポリシータイプすべてにわたるシステム定義のポリシーと、事前定義されたストレージクラスが含まれています。これらのポリシーやクラスはそのまま使用することも、組織の要件に合わせてカスタマイズするための出発点としてコピーすることもできます。link:concept-storage-class-policies.html["ストレージクラスポリシーについて"]。

.ストレージクラスを作成する前に、どのような設定が必要ですか？
ストレージクラスを作成する前に、以下の点を確認してください：

* 少なくとも1つのONTAPクラスターを検出して、Console のローカルデプロイメントが配置時に評価するストレージターゲットを確保してください。
* 組織管理者権限を持っていること。
* ストレージクラスはポリシーから構成されるため、パフォーマンス、容量、その他の要件を反映するストレージクラスポリシーを作成してください。


link:concept-storage-classes.html["ストレージクラスについて"].

.ワークロードがストレージクラスのコンプライアンスから外れた場合、何が起こりますか？
プロビジョニング後、コンソールのローカルデプロイメントは、各ワークロードをストレージクラスに対して継続的に評価します。ワークロードが、クラスタ構成の直接的な変更やパフォーマンスの低下などによって逸脱した場合、コンソールは直ちに違反を検知し、アラートを発します。ガイド付きの修復手順に従うか、自動修復を設定することで、一般的なドリフト状態を解決できます。link:concept-storage-classes.html["ストレージクラスについて"]。



[[storage-fleets-and-folders]]
== ストレージフリートとフォルダー

.ストレージフリートとは何ですか？また、なぜ利用すべきなのでしょうか？
ストレージフリートとは、まとめて管理するストレージシステムをグループ化したものです。ポリシーやアクセス設定をクラスタごとに個別に構成する代わりに、フリートレベルで一度適用することで、フリート内のすべてのクラスタが同じ基準で動作し、反復作業を削減し、動作の一貫性を維持できます。link:concept-storage-fleets.html["ストレージフリートについて"]。

.フォルダーとフリートの違いは何ですか？
フォルダは関連するフリートをグループ化するものであり（例えば、地域別や事業部門別など）、ストレージシステムを直接関連付けることはできません。一方、フリートは管理対象のストレージシステムをまとめてグループ化します。フォルダは、組織化とアクセス権限の委譲のためのツールであり、IAM権限を持たないメンバーには表示されません。メンバーはフォルダではなく、フリートにアクセスします。link:concept-folders-fleets-overview.html["フォルダーとフリートについて"]。

.ストレージクラスをフリートに関連付けると、プロビジョニングにどのような影響がありますか？
ストレージクラスをフリートに関連付けると、コンソールのローカルデプロイメントは、そのクラスのポリシーをフリート内のすべてのプロビジョニングに適用します。フリートにプロビジョニングされたワークロードは、管理者が設定を選択または検証することなく、パフォーマンス、容量、および階層化ルールを自動的に継承するため、フリートとクラスの関連付けは、クラスター全体で一貫した標準を適用するための主要な手段となります。link:concept-storage-fleets.html["ストレージフリートについて"]。



[[provisioning-storage]]
== ストレージのプロビジョニング

.NetApp Console のローカル展開でサポートされているプロビジョニング方法は何ですか？
NetApp Console のローカル展開では、3つのプロビジョニングワークフローがサポートされており、いずれもストレージクラスを適用し、RBACと監査ログによって管理されます。

* *手動プロビジョニング*：対象システムと構成の詳細を選択して、明確な制御を行います。
* *自動プロビジョニング*：ワークロードの入力とオプションのストレージクラスを指定すると、NetApp Console が最適な配置を推奨します。
* *AI支援（エージェント）プロビジョニング*：必要なものを自然言語で説明すると、Console がプランを提案し、お客様が確認・承認してからプロビジョニングが実行されます。


link:concept-manage-storage.html["ストレージの管理について"].



[[monitoring-and-alerts]]
== 監視とアラート

.ストレージの状態とパフォーマンスを監視するにはどうすればよいですか？
NetApp Console のローカル展開では、フリート全体の健全性とパフォーマンスのダッシュボードが提供され、注意が必要なクラスターやボリュームを特定できます。また、ワークロードアナライザーを使用してボリュームを詳細に調査したり、設定可能なアラートや通知、ガイド付きまたは自動の修復を実行したりできます。link:concept-monitor-storage.html["ストレージ監視について"]。

.ワークロードアナライザーは何をするものですか？
ワークロードアナライザーは、単一ボリュームの経時的な動作を表示し、レイテンシ、スループット、IOPS、リソース使用率、容量、構成変更を同じウィンドウ内で相関させることで、根本原因を特定できるようにします。ストレージ層か、ネットワーク層などの他の層か、アプリケーションの問題の原因を特定するのに役立ち、アナライザーから直接、修正推奨事項を実行できます。link:concept-workload-analyzer.html["ワークロードアナライザーについて"]。

.パフォーマンスチャートが正常に見える場合でも、ボリュームのレイテンシが高くなることがあるのはなぜでしょうか？
利用可能な容量が少ないことが原因である可能性があります。ONTAPシステムが85%以上使用されている場合、高い使用率自体がパフォーマンスの問題を引き起こす可能性があります。そのため、ワークロードアナライザーの容量セクションでは、パフォーマンスチャートだけでは説明できないレイテンシについて説明できます。link:concept-workload-analyzer.html["ワークロードアナライザーについて"]。

.NetApp Console のローカル展開におけるアラートはどこから来るのか、またどのように分類されるのか？
アラートは、検出されたクラスター上の ONTAP イベント管理システム（EMS）および NetApp Backup and Recovery の操作から発信され、組織全体で一元的に表示されます。各アラートには、影響を受けるシステム、重大度（重大、警告、情報など）、および影響範囲（容量、接続性、データ保護、パフォーマンス、セキュリティなど）が示されます。コンソールには、お客様の権限で許可されているフリートのアラートのみが表示されます。link:concept-console-alerts.html["アラートについて"]。

.アラート通知ルールは、誰に通知するかをどのように決定するのですか？
通知ルールは、サービス、重要度、影響範囲、および対象システムに基づいてアラートを照合し、指定されたアクセス権限を持つユーザーに電子メールまたはWebhook経由で通知を配信します。なお、これらのルールは特定のシステムに適用され、フリート全体には適用されません。また、計画メンテナンス期間中はミュートにすることができます。コンソールにはデフォルトのルールが含まれており、カスタムルールを作成することもできます。link:concept-console-alerts.html["アラートについて"]。

.カスタムダッシュボードでは何ができますか？
カスタムダッシュボードを使用すると、定義済みのテンプレートからカードを組み合わせ、範囲、メトリック、集計方法、対象リソース、および時間枠を選択することで、パーソナライズされた監視ビューを作成できます。テンプレートはパフォーマンス、容量、健全性、アラートをカバーし、カードを ONTAP 階層の任意のレベルにスコープできます。各ダッシュボードとカードはお客様専用のものであり、お客様が閲覧を許可されているリソースのデータのみが表示されます。link:concept-custom-dashboards.html["NetApp Console ローカル展開におけるカスタムダッシュボードについて"]。



[[identity-and-access]]
== IDとアクセス

.ロールベースのアクセス制御は、NetApp Console のローカル展開においてどのように機能しますか？
RBACを使用すると、組織、フォルダー、またはフリートレベルで、定義済みの最小権限ロールをメンバーに割り当てることができます。同じロールであっても、割り当てるスコープによって有効なアクセス権限が異なります。これにより、中央管理者には広範なアクセス権限を付与しつつ、地域管理者やチーム管理者にはそれぞれが管理するフリートへのアクセス権限を制限できます。link:concept-iam-rbac.html["ロールベースアクセス制御について学ぶ"]。

.ロールベースの継承はどのように機能するのですか？また、下位スコープでそれを上書きすることはできますか？
組織レベルまたはフォルダレベルで割り当てられた役割は、その下にあるすべての子フォルダ、フリート、およびリソースに継承されるため、フォルダとフリートの設計によって、割り当てがどの程度広範囲に適用されるかが決まります。下位スコープで継承されたアクセス権を上書きすることはできません。変更するには、最初にアクセス権を付与した上位スコープでの割り当てを変更してください。link:concept-iam-rbac.html#role-inheritance["NetApp Console ローカル展開におけるロール継承について"]。

.どのようなカテゴリの事前定義済みロールが利用可能ですか？
NetApp Console のローカル展開グループは、定義済みのロールを次の3つのカテゴリに分類します。

* *プラットフォームロール*：組織管理者、フォルダーまたはフリート管理者、フェデレーション管理者、スーパー管理者またはスーパービューアーなどのコンソール管理権限。
* *アプリケーションロール*：ストレージ管理者、ストレージビューアー、運用サポートアナリストなどのストレージおよび監視権限。
* *データ サービス ロール*：バックアップ/リカバリ ロールや分類ビューアなど、特定のデータ サービスに対するアクセス許可。


link:reference-iam-predefined-roles.html["事前定義されたアクセスロールについて"].

.なぜ NetApp Console のローカル展開を Active Directory と統合する必要があるのですか？
Active Directoryとの統合により、ユーザーは既存の企業認証情報でサインインできるようになり、個別のコンソールパスワードが不要になるほか、管理者はアクセス権を割り当てる際にディレクトリ内のユーザーを検索できるようになります。認可は引き続き独立して管理されます。Console は、各メンバーが実行できる操作を制御するために独自のロールを使用します。link:concept-secure-access.html["セキュアアクセスの詳細"]。

.コンソール ユーザーの場合、多要素認証はどのように機能しますか？
ローカルユーザーは、多要素認証（MFA）を有効にすることで、認証情報が漏洩した場合の不正アクセスリスクを軽減する追加の認証手順を導入できます。ディレクトリ認証ユーザーは、コンソールのローカル展開を通じてMFAを有効にすることはできません。link:concept-secure-access.html["セキュアアクセスの詳細"]。



[[ai-assisted-management]]
== AI支援管理

.NetApp Console のローカル展開では、AI支援管理のためにどのLLMプロバイダーがサポートされていますか？
リリースおよびエンドポイントでサポートされているプロバイダータイプ（OpenAI、OpenAI互換、またはAnthropic）に対応するサブスクリプションまたはサービスアクセスを、ご自身でご用意ください。次に、設定時に有効なAPIキーを入力します。統合を構成するには、設定されたエンドポイントへのアウトバウンドネットワーク接続と、組織管理者またはスーパー管理者の権限も必要です。link:concept-llm-integration.html["LLM統合について"]。

.LLM 統合を有効にすると、ストレージ データやクエリがサードパーティ サービスに送信されますか？
コンソールは、設定したLLMエンドポイントにのみプロンプトと関連コンテキストを送信します。そのエンドポイントがサードパーティのクラウド サービスである場合、データはHTTPS経由でそのサービスに送信されます。そのエンドポイントがOpenAI互換の内部サービスである場合、その統合に関するデータは内部経路上に留まります。AIによるすべての操作はお客様のRBACを尊重し、機密性の高い操作にはお客様の承認が必要です。link:concept-llm-integration.html["LLM統合について"]。

.Console アシスタントでできることと、ストレージへの変更を制御する方法について
LLMを接続すると、NetApp Consoleアシスタントによって、ユーザーはガイダンスを取得したり、サポートされているメトリックを分析したり、ストレージをプロビジョニングしたり、アラートを調査したり、自然言語を使用してサポートされているONTAP操作をリクエストしたりできるようになります。*読み取り専用*モードでは、アシスタントは変更を行いません。*読み取り/書き込み*モードでは、実行前に確認と承認のために、ストレージを変更する提案された操作が表示されます。link:task-console-asst-use.html["NetApp Console アシスタントを使用する"]。

.コンソールアシスタントはどのような操作をサポートしていますか？
コンソールアシスタントは、会話型ガイダンス、サポートされている読み取り専用のメトリクス分析、ストレージ プロビジョニング、アラート調査、および選択された ONTAP 管理操作をサポートしています。利用可能な操作は、リリース、設定されたエンドポイント、およびお客様のロールとリソーススコープによって異なります。link:reference-console-assistant-operations.html["サポートされているコンソールアシスタント操作を参照してください"]。

.コンソールアシスタントが非同期操作を実行するとどうなりますか？
すぐに完了しないサポートされている操作については、アシスタントがジョブを作成し、リクエストについて問い合わせた際に現在のステータスを返すことができます。link:task-console-asst-use.html["NetApp Console アシスタントを使用する"]。



[[data-protection-and-auditing]]
== データ保護と監査

.NetApp Console のローカル展開で利用できるデータ保護機能にはどのようなものがありますか？
NetApp Console のローカル展開により、NetApp Backup and Recovery にアクセスできるようになります。これにより、同じインターフェースからデータのバックアップと復元が可能になり、ガバナンスの一貫性を保ちながら、チームが使用するツールの数を削減できます。link:concept-data-services.html["データサービスについて学ぶ"]。

.NetApp Console のローカル展開は、監査とログ保持をどのようにサポートしていますか？
すべての管理操作は監査記録を生成し、監査ページから確認およびフィルタリングできます。監査ログをWebhookを介して独自のsyslogサーバーにエクスポートすることで、集中監視ツールやSIEMツールに送信して長期保存と分析が可能になります。また、Console はお客様の環境内で実行されるため、ログデータがお客様のインフラストラクチャの外部に送信されることはありません。link:task-audit-console-activity.html["NetApp Consoleのローカル デプロイ アクティビティの監査"]。
